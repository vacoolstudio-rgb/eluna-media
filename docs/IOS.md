# iOS: что сделано вслепую и что нужно проверить на Mac

Весь iOS-код этого приложения написан без Mac. Он компилировался ровно ноль раз,
на устройстве не запускался ни разу, и симулятора никто не открывал. Android
проверен на WP30 Pro и покрыт интеграционными тестами; здесь ни одного из этих
доказательств нет.

Документ существует, чтобы человек с Mac мог продолжить, не разбирая заново, что
именно недоделано и почему. **Порядок разделов — порядок работы**: первое даёт
работающую сборку, последнее — необязательно.

Правило для всего ниже: iOS-код писался «отказывать закрыто» — любая ветка,
которая не является подтверждённым успехом, возвращает в Dart `false`/`null`.
Поэтому худшее, что должно случиться на непроверенном пути, — кнопка, которая
ничего не делает. Если увидите иное, это баг, а не задумка.

---

## 0. Прежде всего: собрать

```bash
flutter pub get
cd ios && pod install && cd ..
flutter build ios --debug --no-codesign
```

Ожидаемые места, где может сломаться в первый раз:

- **`pod install`** — `Podfile.lock` в репозитории есть, но подов никто не
  ставил. Версии `ffmpeg_kit_flutter_new` для iOS тянут крупные фреймворки.
- **Bundle id разный на платформах.** iOS: `com.lunara.elunaMedia`
  (`PRODUCT_BUNDLE_IDENTIFIER` в `project.pbxproj`). Android:
  `com.lunara.eluna_media`. В `Eluna.configure` (`lib/main.dart`) записан
  андроидный — это **осознанно**, он там используется для ссылок на магазин, а
  не как идентификатор сборки. Не «чинить» их в одинаковые: переименование
  bundle id на iOS создаёт новое приложение.
- **Свободных иконок в корне бандла больше нет** — см. раздел 1.

## 1. Иконка приложения и девять сменных

**Состояние: реализовано целиком, не собиралось.** Это единственная часть iOS,
сделанная так, чтобы на Mac не потребовалось ручных действий в Xcode.

Как устроено:

- `tool/gen_app_icons.py` собирает всё из мастеров `design/app_icons/*.webp`.
  Запуск — `python tool/gen_app_icons.py`, зависимость одна (Pillow).
- Основная иконка — `ios/Runner/Assets.xcassets/AppIcon.appiconset` (имена
  файлов прежние, `Contents.json` не трогался).
- Каждая альтернативная — **свой набор** `AppIcon-<id>.appiconset` в том же
  каталоге. У них нет размера `ios-marketing` (1024): он нужен App Store, а не
  домашнему экрану, и восемь копий по мегабайту не нужны никому.
- В `project.pbxproj` во **всех трёх** конфигурациях (Debug/Release/Profile)
  прописано:

  ```
  ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES = "AppIcon-petals AppIcon-toolbox …";
  ASSETCATALOG_COMPILER_INCLUDE_ALL_APPICON_ASSETS = YES;
  ```

- `Info.plist` иконки **не перечисляет**. `CFBundleIcons` генерирует Xcode из
  каталога; рукописный блок рядом либо перезаписал бы сгенерированный, либо
  ссылался бы на файлы, которых нет.
- Переключение: `AppDelegate.swift`, метод `setAppIcon` канала
  `eluna/share_intake` → `UIApplication.setAlternateIconName`. Dart шлёт
  `iosName` = `AppIcon-<id>`, а для иконки по умолчанию — **`null`**, потому что
  «вернуть основную» в этом API выражается именно null, а не именем набора.

Почему не свободные файлы в корне бандла (прежний способ, он же самый
распространённый в интернете): у него есть шаг, который невозможно выполнить вне
Xcode — добавить файлы в target вручную. Для проекта, который собирают на чужой
машине, это означало бы «иконки не работают, пока кто-то не кликнет». Каталог
ассетов такого шага не требует.

**Что проверить:**

1. Собралось без ошибок каталога ассетов.
2. В собранном `.app` лежат файлы вида `AppIcon-petals60x60@2x.png`:
   ```bash
   find build/ios -name 'AppIcon-*60x60@2x.png' | head
   ```
   Если их нет — настройки сборки не подхватились, и дальше проверять нечего.
3. На устройстве: Настройки → Иконка приложения → выбрать не-дефолтную. Домашний
   экран должен смениться, и iOS покажет свой системный алерт «Значок изменён» —
   это её поведение, а не наше.
4. Вернуть дефолтную — иконка обязана вернуться к `loop`.

**Известное ограничение:** `supportsAlternateIcons` бывает `false` (некоторые
корпоративные конфигурации). Тогда `setAppIcon` вернёт `false`, экран покажет
`appIconFailed` и **не** отметит плитку выбранной. Это правильное поведение, не
баг.

**Чего у iOS нет и не планируется:** аналога `<activity-alias>`, поэтому
андроидная проверка «включена ровно одна запись» здесь неприменима. И нет
аналога `getComponentEnabledSetting` — прочитать обратно можно только
`UIApplication.shared.alternateIconName`; если будете писать тест, читать надо
именно его.

## 2. Приём файлов извне

Здесь три отдельные вещи, и путать их не надо.

| Что | Состояние |
|---|---|
| «Открыть в Eluna Media» для файла | Написано, не проверено |
| Приём из системного листа «Поделиться» | **Не сделано**, нужен новый target |
| Открытие по URL | Написано, не проверено |

- **Открыть с помощью.** `CFBundleDocumentTypes` в `Info.plist` +
  обработка URL в `AppDelegate.swift`, канал тот же `eluna/share_intake`.
  Проверить: из «Файлов» открыть видео «в приложении Eluna Media» — файл должен
  оказаться в очереди.
- **Share-in (лист «Поделиться»).** Требует **отдельного Share Extension
  target**, которого в проекте нет: extension — это самостоятельный бинарник со
  своим bundle id и своим Info.plist, и создать его можно только в Xcode. Обмен
  файлами между extension и приложением делается через App Group. На Android эта
  функция работает и покрыта; на iOS её просто нет.

## 3. Удаление оригиналов

**Состояние: написано, на устройстве не запускалось.**

`PHPhotoLibrary`, подтверждение всегда системное — приложение само ничего не
удаляет. Написано «отказывать закрыто»: любой путь, кроме подтверждённого
удаления, сообщает ноль удалённых, поэтому худший исход — кнопка не делает
ничего.

**Существенная разница с Android, которую нельзя «исправить»:** iOS ищет
оригинал **только по имени файла**. Android сверяет имя *и* точный размер в
байтах. Причина не в лени: `PHAsset` не отдаёт размер файла публичным API.
Значит, на iOS выше шанс, что совпадений окажется несколько, и тогда элемент
**пропускается** — это правильный выбор, удалять «похожий» файл нельзя.

Проверять на устройстве с реальной медиатекой, а не на пустом симуляторе:
интересны как раз случаи «два файла с одинаковым именем».

## 4. Фоновая работа

`ForegroundService` на iOS — **осознанный no-op**. Аналога foreground service в
iOS нет. Конверсия идёт, пока приложение на экране; что происходит с длинной
конверсией при сворачивании — **не проверено**, и это первый кандидат на
неприятный сюрприз. Ожидание: iOS даст несколько минут, потом приостановит
процесс, и FFmpeg-сессия оборвётся.

Если окажется, что обрывается — честный вариант поведения: поймать переход в
background и показать при возврате, что работа прервана, а не делать вид, что
всё идёт.

## 5. Чего на iOS нет вовсе

- **Сохранение в «Загрузки»** — у iOS нет такой папки. `openDownloads`
  возвращает `false`, и Dart подставляет лист «Поделиться». Это не заглушка «на
  потом», а окончательное решение.
- **Отмена из уведомления** — сделана через андроидный foreground service.
- **`vp9_mediacodec` и прочее MediaCodec** — андроидное. На iOS аппаратный путь
  идёт через VideoToolbox, и `EncoderCatalog` его уже ищет
  (`h264_videotoolbox`, `hevc_videotoolbox`).

  **Есть ли он там на самом деле — неизвестно, и выяснить это надо первым
  делом.** iOS-фреймворк ffmpeg-kit — отдельный бинарник со своей строкой
  `configure`; андроидная (в ней videotoolbox выключен, что на Android ничего и
  не значит) о нём не говорит ничего. Ответ печатает
  `integration_test/encoder_inventory_test.dart` — он выводит баннер и строку
  `configure` той сборки, на которой запущен. Запустите его на iPhone и
  посмотрите: если `videotoolbox` выключен, аппаратного кодирования на iOS нет
  вовсе и всё пойдёт софтверно — это надо либо принять, либо решать вместе с
  пересборкой FFmpeg (`docs/FFMPEG_BUILD.md`).

  Отдельно помните находку с Android: **наличие энкодера в `-encoders` не
  доказывает, что железо есть.** Для VideoToolbox это тоже верно.

## 6. Что запустить на Mac в первую очередь

```bash
flutter test                                   # 281 тест, платформа не нужна
flutter test integration_test -d <iphone>      # вот это никто не запускал
```

Интеграционные наборы писались под Android, но почти все из них платформы не
касаются — они гоняют FFmpeg. Ожидание: пройдут. Расхождения будут интересны
сами по себе, потому что означают разницу в сборке FFmpeg между платформами.

`integration_test/app_icon_test.dart` — **исключение, он андроидный**:
`AppIconService.currentAlias()` возвращает `null` вне Android, а проверки идут
по псевдонимам `<activity-alias>`. Для iOS нужен свой тест поверх
`alternateIconName` (см. раздел 1).
