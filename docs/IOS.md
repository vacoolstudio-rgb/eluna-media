# iOS: что сделано вслепую и что уже проверено на Mac

Весь iOS-код этого приложения написан без Mac. **16 августа 2026 года он впервые
собрался и впервые запустился** — на симуляторе iPhone 17 Pro Max, iOS 26.5,
Xcode 26.6, Flutter 3.44.6. Собралось с первого раза, без единой правки кода.

Что теперь доказано, а что нет:

| | Состояние |
|---|---|
| Сборка под iOS | **Проверена.** `pod install` и `flutter build` проходят |
| Запуск приложения | **Проверен** на симуляторе |
| Конвертация, сжатие, улучшение | **Проверены**: 165 интеграционных тестов на симуляторе, все зелёные |
| Наличие иконок в бандле, смена иконки | **Проверены** (раздел 1) |
| Аппаратные энкодеры VideoToolbox | **Проверены и работают** (раздел 5) |
| Приём файлов извне | Не проверен — нужен человек с «Файлами» (раздел 2) |
| Удаление оригиналов | Проверено только «отказывать закрыто» (раздел 3) |
| Поведение при сворачивании | **Не проверено** (раздел 4) |
| Настоящее устройство | **Ничего не проверено**: сборка на iPhone требует подписи |

Документ существует, чтобы человек с Mac мог продолжить, не разбирая заново, что
именно недоделано и почему. **Порядок разделов — порядок работы**: первое даёт
работающую сборку, последнее — необязательно.

Правило для всего ниже: iOS-код писался «отказывать закрыто» — любая ветка,
которая не является подтверждённым успехом, возвращает в Dart `false`/`null`.
Поэтому худшее, что должно случиться на непроверенном пути, — кнопка, которая
ничего не делает. Если увидите иное, это баг, а не задумка.

## 0. Прежде всего: собрать

```bash
flutter pub get
cd ios && pod install && cd ..
flutter build ios --debug --simulator     # или --no-codesign для устройства
```

**Проверено: проходит.** `pod install` ставит 22 пода (22 из 18 объявленных),
включая `ffmpeg_kit_flutter_new` 8.1.2; сборка занимает около минуты.

Что стоит знать:

- **`Podfile.lock` в репозитории не было** — вопреки тому, что тут раньше было
  написано. Он появляется после первого `pod install`, и его надо закоммитить:
  без него версии подов у следующего человека разъедутся.
- **`pod install` дописывает две строки** в `ios/Flutter/Debug.xcconfig` и
  `Release.xcconfig` (`#include?` на `Pods-Runner.*.xcconfig`) и правит
  `project.pbxproj`. Это не мусор — без этих строк поды не линкуются. Тоже в
  коммит.
- **CocoaPods ругается на конфигурацию Profile**: она наследует
  `Release.xcconfig`, а под неё сгенерирован отдельный
  `Pods-Runner.profile.xcconfig`. На Debug и Release не влияет; `flutter build
  ios --profile` до этого никто не собирал.
- **Bundle id — `com.eluna.media`, один на обе платформы** и на семейном
  шаблоне `com.eluna.*`, как у читалки, трекера и бюджета
  (`PRODUCT_BUNDLE_IDENTIFIER` в `project.pbxproj`, `applicationId` и
  `namespace` в `android/app/build.gradle.kts`, `packageId` в `Eluna.configure`).
  До 2026-08-16 здесь стояли `com.lunara.elunaMedia` и `com.lunara.eluna_media`
  — разные на платформах и вне шаблона. Переименовать вышло без последствий
  ровно потому, что приложение ещё нигде не выпущено: **после первой публикации
  этого сделать уже нельзя** — на iOS новый bundle id это новое приложение, на
  Android новый `applicationId` рвёт обновления у тех, кто уже поставил.
- **Подписи нет.** `DEVELOPMENT_TEAM` в проекте не задан, поэтому на настоящий
  iPhone это пока не ставится — нужен Apple ID и команда в Xcode.
- **Свободных иконок в корне бандла больше нет** — см. раздел 1.

## 1. Иконка приложения и девять сменных

**Состояние: реализовано целиком, не собиралось.** Это единственная часть iOS,
сделанная так, чтобы на Mac не потребовалось ручных действий в Xcode.

Как устроено:

- `tool/gen_app_icons.py` собирает всё из мастеров `design/app_icons/*.webp`.
  Запуск — `python tool/gen_app_icons.py`, зависимость одна (Pillow).
- Основная иконка — `ios/Runner/Assets.xcassets/AppIcon.appiconset` (имена
  файлов прежние, `Contents.json` не трогался).
- Каждая альтернативная — **свой набор** `AppIcon-<id>.appiconset` в том же
  каталоге. У них нет размера `ios-marketing` (1024): он нужен App Store, а не
  домашнему экрану, и восемь копий по мегабайту не нужны никому.
- В `project.pbxproj` во **всех трёх** конфигурациях (Debug/Release/Profile)
  прописано:

  ```
  ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES = "AppIcon-petals AppIcon-toolbox …";
  ASSETCATALOG_COMPILER_INCLUDE_ALL_APPICON_ASSETS = YES;
  ```

- `Info.plist` иконки **не перечисляет**. `CFBundleIcons` генерирует Xcode из
  каталога; рукописный блок рядом либо перезаписал бы сгенерированный, либо
  ссылался бы на файлы, которых нет.
- Переключение: `AppDelegate.swift`, метод `setAppIcon` канала
  `eluna/share_intake` → `UIApplication.setAlternateIconName`. Dart шлёт
  `iosName` = `AppIcon-<id>`, а для иконки по умолчанию — **`null`**, потому что
  «вернуть основную» в этом API выражается именно null, а не именем набора.

Почему не свободные файлы в корне бандла (прежний способ, он же самый
распространённый в интернете): у него есть шаг, который невозможно выполнить вне
Xcode — добавить файлы в target вручную. Для проекта, который собирают на чужой
машине, это означало бы «иконки не работают, пока кто-то не кликнет». Каталог
ассетов такого шага не требует.

**Что проверено (16.08.2026, симулятор):**

1. Собралось без ошибок каталога ассетов. ✔
2. В `.app` лежат все восемь: `AppIcon-{petals,toolbox,neon,orbit,unbox,clamp,
   envelope,satchel}60x60@2x.png`, и Xcode сам сгенерировал `CFBundleIcons` с
   `CFBundleAlternateIcons` — рукописного блока в `Info.plist` действительно не
   нужно. ✔
   ```bash
   find build/ios -name 'AppIcon-*60x60@2x.png' | head
   ```
3. Смена работает: `setAlternateIconName` возвращает успех, и iOS показывает
   свой системный алерт «You have changed the icon for “Eluna Media”» уже с
   новой картинкой. ✔

**Чем это покрыто в тестах — и почему не так, как на Android.**

Андроидный `integration_test/app_icon_test.dart` перебирает все девять иконок
подряд. На iOS так нельзя, и это не лень: **успешная смена поднимает системный
алерт, и до нажатия OK прогон стоит**. Проверено — цикл встал на первой же
настоящей смене и не сдвинулся. Нажать эту кнопку интеграционный тест не может:
она вне Flutter-иерархии, а `simctl` тапов не умеет.

Поэтому проверка разложена на два файла:

- `test/ios_project_test.dart` (**хостовый, без устройства**) — что все восемь
  наборов есть в каталоге ассетов, что каждый перечислен в
  `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES` во **всех трёх**
  конфигурациях, и что `Info.plist` не перечисляет иконки руками. Это ловит
  ровно тот класс расхождений, ради которого писался андроидный двойник.
- `integration_test/ios_platform_test.dart` (**на устройстве**) — что канал
  отвечает, что чтение возвращает факт и что мусорное имя отвергается. Алерт на
  этих путях не поднимается.

Само переключение на живую остаётся ручной проверкой — пункт 3 выше.

**Известное ограничение:** `supportsAlternateIcons` бывает `false` (некоторые
корпоративные конфигурации). Тогда `setAppIcon` вернёт `false`, экран покажет
`appIconFailed` и **не** отметит плитку выбранной. Это правильное поведение, не
баг.

**Чего у iOS нет:** аналога `<activity-alias>`, поэтому андроидная проверка
«включена ровно одна запись» здесь неприменима. Прочитать обратно можно только
`UIApplication.shared.alternateIconName` — это и делает метод `appIconAlias`
канала `eluna/share_intake`, а `AppIconService.currentIconId()` переводит ответ
в `id`, чтобы обе платформы отвечали на один вопрос одинаково. У основной иконки
имени нет вовсе: там `nil`, и это означает «включена стандартная», а не «не
знаю».

## 2. Приём файлов извне

Здесь три отдельные вещи, и путать их не надо.

| Что | Состояние |
|---|---|
| «Открыть в Eluna Media» для файла | Написано, не проверено |
| Приём из системного листа «Поделиться» | **Не сделано**, нужен новый target |
| Открытие по URL | Написано, не проверено |

- **Открыть с помощью.** `CFBundleDocumentTypes` в `Info.plist` +
  обработка URL в `AppDelegate.swift`, канал тот же `eluna/share_intake`.
  Проверить: из «Файлов» открыть видео «в приложении Eluna Media» — файл должен
  оказаться в очереди.
- **Share-in (лист «Поделиться»).** Требует **отдельного Share Extension
  target**, которого в проекте нет: extension — это самостоятельный бинарник со
  своим bundle id и своим Info.plist, и создать его можно только в Xcode. Обмен
  файлами между extension и приложением делается через App Group. На Android эта
  функция работает и покрыта; на iOS её просто нет.

## 3. Удаление оригиналов

**Состояние: написано, на устройстве не запускалось.**

`PHPhotoLibrary`, подтверждение всегда системное — приложение само ничего не
удаляет. Написано «отказывать закрыто»: любой путь, кроме подтверждённого
удаления, сообщает ноль удалённых, поэтому худший исход — кнопка не делает
ничего.

**Существенная разница с Android, которую нельзя «исправить»:** iOS ищет
оригинал **только по имени файла**. Android сверяет имя *и* точный размер в
байтах. Причина не в лени: `PHAsset` не отдаёт размер файла публичным API.
Значит, на iOS выше шанс, что совпадений окажется несколько, и тогда элемент
**пропускается** — это правильный выбор, удалять «похожий» файл нельзя.

Проверять на устройстве с реальной медиатекой, а не на пустом симуляторе:
интересны как раз случаи «два файла с одинаковым именем».

**Автоматизировать это не вышло, и вот почему** — чтобы следующий человек не
потратил на попытку вечер. Любой вызов с непустым списком доходит до
`requestPhotoAccess`, а тот на свежей установке поднимает системный запрос
доступа. Нажать в нём из интеграционного теста некому, и прогон не падает, а
**встаёт** до таймаута. Выдать доступ заранее тоже не получается:
`xcrun simctl privacy <udid> grant photos com.eluna.media` на iOS 26 не
покрывает readWrite-доступ к `PHPhotoLibrary`, и `grant all` тоже — запрос
появляется всё равно (проверены оба). А дальше, даже с доступом, стоит второй
системный диалог — само подтверждение удаления, и вот он там по замыслу.

Что покрыто автоматически: пустой список отвечает нулём, не доходя до канала
(`integration_test/ios_platform_test.dart`). Остальное — руками.

Та же причина делает системный запрос доступа единственным местом, где видно,
что строки `NSPhotoLibraryUsageDescription` и `NSPhotoLibraryAddUsageDescription`
действительно попадают в диалог. Попали: текст про альбом «Eluna Media» на
экране был.

## 4. Фоновая работа

`ForegroundService` на iOS — **осознанный no-op**. Аналога foreground service в
iOS нет. Конверсия идёт, пока приложение на экране; что происходит с длинной
конверсией при сворачивании — **не проверено**, и это первый кандидат на
неприятный сюрприз. Ожидание: iOS даст несколько минут, потом приостановит
процесс, и FFmpeg-сессия оборвётся.

Если окажется, что обрывается — честный вариант поведения: поймать переход в
background и показать при возврате, что работа прервана, а не делать вид, что
всё идёт.

## 5. Чего на iOS нет вовсе

- **Сохранение в «Загрузки»** — у iOS нет такой папки. `openDownloads`
  возвращает `false`, и Dart подставляет лист «Поделиться». Это не заглушка «на
  потом», а окончательное решение.
- **Отмена из уведомления** — сделана через андроидный foreground service.
- **`vp9_mediacodec` и прочее MediaCodec** — андроидное. На iOS аппаратный путь
  идёт через VideoToolbox, и `EncoderCatalog` его уже ищет
  (`h264_videotoolbox`, `hevc_videotoolbox`).

  **Вопрос закрыт: VideoToolbox в iOS-сборке есть и он работает.** В строке
  `configure` того бинарника стоит `--enable-videotoolbox` (на Android — не
  стоит), `-encoders` перечисляет `h264_videotoolbox` и `hevc_videotoolbox`, и
  главное — `pipeline_extras_test.dart` ими **действительно закодировал**:

  ```
  АППАРАТНО: h264 закодирован через h264_videotoolbox
  АППАРАТНО: h265 закодирован через hevc_videotoolbox
  ```

  То есть на iOS аппаратный путь живее, чем на Android, где videotoolbox
  выключен, а MediaCodec отвечает `NAME_NOT_FOUND` на половину заявленного.
  Пересборка FFmpeg (`docs/FFMPEG_BUILD.md`) ради этого не нужна.

  Проверено пока **только на симуляторе**, а он кодирует через медиадвижок
  самого Mac. На настоящем iPhone это надо подтвердить заново — и помнить
  находку с Android: **наличие энкодера в `-encoders` не доказывает, что железо
  есть.** Для VideoToolbox это тоже верно.

  `vp9` и `av1` аппаратно на iOS не нашлись — тест честно печатает
  `ПРОПУЩЕНО: у этого устройства нет аппаратного vp9`, и обе идут софтверно.

## 7. Что осталось непроверенным

По убыванию того, насколько неприятным может оказаться сюрприз:

1. **Настоящий iPhone.** Всё выше — симулятор. `DEVELOPMENT_TEAM` в проекте не
   задан, поэтому сборка на устройство требует Apple ID и настройки подписи.
   Отдельно важно для VideoToolbox: симулятор кодирует медиадвижком Mac.
2. **Сворачивание во время длинной конверсии** — раздел 4, до сих пор ничем не
   тронуто.
3. **«Открыть в Eluna Media»** — раздел 2, нужен человек с «Файлами».
4. **Удаление оригиналов на живой медиатеке** — раздел 3.
5. **Face ID.** Строка `NSFaceIDUsageDescription` теперь в `Info.plist` (её там
   не было, а без неё iOS убивает процесс при первом обращении к Face ID —
   SIGABRT от системы, который `try/catch` вокруг `BiometricGate` не поймает).
   Наличие строки стережёт `test/ios_project_test.dart`; что сам запрос Face ID
   проходит, на устройстве никто не смотрел.

## 8. Плиточный HEIC: что нашли, чем починили, что осталось

**Находка.** Снимок с айфона — это HEIC, разрезанный на плитки 512×512 и
собираемый элементом `grid`. Встроенный FFmpeg выдавал вместо кадра 1024×768
ровно 512×512, то есть левый верхний угол, и сообщал об успехе. Пользователь
получал молча обрезанную фотографию — худший из возможных исходов, и на iOS не
мелочь: HEIC здесь основной формат снимков.

Нашлось это только потому, что в пустой слот фикстуры положили настоящий файл.
Прежняя проверка «результат больше 2000 байт» одну плитку пропускала — плитка
тоже весит килобайты.

**Причина — не в сборке FFmpeg.** Бинарник спросили напрямую: демуксер плитку
разбирает и знает настоящий размер.

```
Stream group #0:0[0x5]: Tile Grid: hevc (hvc1), yuvj420p, 1024x768 (default)
```

Не хватает только сшивки в командном слое: и умолчание, и `-map 0:g:0`, и
`-map 0:v` одинаково отдают одну плитку. Плитки при этом лежат обычными
потоками `0:0`…`0:3`, и собрать их можно фильтром — проверено, даёт ровно
1024×768:

```
-filter_complex "[0:0][0:1][0:2][0:3]xstack=inputs=4:layout=0_0|w0_0|0_h0|w0_h0[s];
                 [s]crop=1024:768:0:0[v]" -map "[v]"
```

**Чем починили — и почему не этим.** Сшивать самим соблазнительно (ничего
нативного), но геометрию сетки надо откуда-то взять, а итоговый размер кадра
FFprobeKit в структурированных данных **не отдаёт** — он есть только текстом в
логе строкой `Tile Grid`. Разбор лога регуляркой ломается от версии к версии, и
это ещё до того, как вспомнить, что снимок 4032×3024 — это 48 плиток.

Поэтому декодирует система: `StillDecoder` (`lib/core/still_decoder.dart`) зовёт
метод `decodeStill` канала `eluna/share_intake`, `AppDelegate` раскодирует файл
через ImageIO в полноразмерный PNG, и до FFmpeg доезжает обычная картинка.
Подстановка живёт в `FFmpegConverter.convert`, поэтому её видят все ветки сразу
— и целевой размер, и два прохода, и поиск качества. Временный PNG удаляется в
`finally`.

Это тот же декодер, которым снимок рисуется в «Фото», так что плитка,
ориентация из EXIF (`kCGImageSourceCreateThumbnailWithTransform`) и цветовое
пространство обрабатываются правильно по определению. Цена — временный файл
(на 12 мегапикселях порядка 30 МБ) и лишнее декодирование; PNG, а не JPEG,
намеренно: это промежуточный файл, и потеря качества на нём была бы вторым
поколением потерь, которого никто не просил.

Отказывает закрыто: любой сбой возвращает `null`, и конвейер работает с
исходником ровно как раньше.

**Android закрыт 16.08.2026.** Там та же сборка FFmpeg и, значит, был тот же
дефект. Половина канала написана в `MainActivity.decodeStill`: `ImageDecoder`
(HEIF с API 28; при `minSdk = 24` на 24–27 системного декодера нет, и метод там
честно возвращает `false`), дальше `Bitmap.compress(PNG)` в переданный путь.
Двадцать минут работы, которые ждали не идеи, а Android SDK: писать вслепую в
рабочую сборку — ровно та ошибка, ради которой существует этот документ.

Теперь SDK на машине стоит, и предположения проверять больше не нужно.
Тест «плитка grid собирается в полный кадр» на эмуляторе API 36 **зелёный** и
печатает `HEIC grid: исходник 1024×768, получилось 1024×768` — там, где раньше
приходила одна плитка 512×512.

Абзац про тест «плитка grid **НЕ** собирается», стоявший здесь раньше, снят
вместе с самим тестом: он сторожил прежнее поведение, а сторожить его больше
незачем. Стережёт обратное — «собирается в полный кадр», и он красный на любой
платформе, где системной половины канала нет.
